### Additional bug found and fixed

Luma initially deducted EUR 5 correctly but omitted the wallet total row. When shipping and wallet
changes leave the quote's grand total unchanged, Magento can skip `sales_quote_save_after`; the stored
preview remained zero. `Controller/Wallet/Apply.php` now saves the preview explicitly after saving the
quote, including reverting an unsupported full-wallet payment. This does not change the wallet balance
or debit coins. The update is scoped to the selected module-owned wallet quote row.

After the fix, the Luma order-summary modal showed the separate EUR -5 row and correct payable total.
Hyva's payment step also showed EUR -5 and EUR 25 payable. Applying zero removed the selection.
Unit and both-store native payment suites were rerun after the fix; final DI compilation passed.
The four ordinary browser orders preceded this wallet-only fix. No new wallet browser order was placed
after it; post-fix browser coverage reached the payment/totals step, and native financial coverage
included actual order placement, invoices, returns and cancellation within rollback transactions.

## Cleanup and remaining limits

All `loyalty/%` configuration rows were compared exactly against the private local snapshot after
restoration. Fictional customer 48's original store data and wallet rows were also compared exactly.
The remaining test quote wallet selection has requested/preview values of zero and no hold. The four
ordinary test orders remain for audit. No outbox events or redemption mutations created since the
browser acceptance started remain in the database.

This is broad local regression evidence, not a claim that every possible configuration is certified.
The following are not covered by a new successful end-to-end test here:

- Online payment-provider success/failure/webhook flows. Offline check/money-order payment was used.
- Email delivery: the demo has no reachable mailcatcher. It also has unrelated Braintree missing-merchant-ID errors.
- New real tenant coin purchases/refunds or live LE-to-Magento synchronization; financial transport was faked.
- Every historical upgrade dataset, a completely new Magento installation and the two skipped legacy-column cases.
- All Hyva releases, merchant-specific checkout/save overrides, or a production-volume load benchmark.
- Every frontend consequence of all 61 settings in every combination. The admin suite saves/validates
  each exposed field; browser checks specifically cover the scenarios listed above.

Tested versions have no remaining blocker found by this pass. Merchant ACC acceptance is still required,
especially before enabling wallet payments with a real PSP. Optional wallet/enrollment features remain
off by default. Publishing the release is a separate action.
